## Foundational verdicts locked 2026-05-16

### V1 — eawfd daemon is Day-1 with smart-spawn writer + daemonless reader

**Decision.** Mutations to `state.json` (and all future stateful surfaces — config layers, registry, event log) route through the eawfd daemon. CLI auto-spawns daemon on demand if not running (tmux / systemd-user / jupyter-kernel pattern); daemon stays alive on idle-timeout (default 300 s, configurable). Reads MAY bypass daemon (direct file IO + Pydantic load) for:

1. **CI environments** without long-running processes
2. **Read-only one-shot CLI calls** (`eawf state show`, `eawf wave list`, `eawf validate`)
3. **Recovery shell** when daemon broken or version-skewed

**Rationale.**

- **Goal 1** ("CLI for agents; TUI/web for operators; daemon for coordination") literally names daemon as coordinator
- **Goal 3** (responsiveness) — daemon push beats mtime poll for sub-second TUI
- **Goal 4** (multi-alpha durability) — migration cost grows monotonically with codebase size; cheapest to pay now
- **Strongest case:** multi-agent parallel dispatch coordination. Today there is NO central coordinator across worktree-isolated waves; daemon = real DAG scheduler + EU budget enforcer + timeout/restart policy + cost accounting chokepoint

**Cost accepted.**

- ~100-file rewrite of state CLI as RPC client (covered by C02 + C05)
- Two-path complexity bounded: writes always through daemon; reads bypass only in 3 named cases above
- New error class: daemon supervisor / PID / socket cleanup / version skew matrix (covered by C02)
- Cold-spawn latency: ~200-400 ms first-call penalty (vs ~120 ms direct); warm-spawn: ~5-10 ms IPC + faster (state cached). Acceptable for stated goals.

**Hard non-negotiables.**

- Daemon is NEVER required for read paths in CI gates
- Daemon spawn MUST be transparent to one-shot CLI users (auto-spawn + auto-shutdown on idle)
- Daemon protocol versioned; CLI fails fast on version skew with clear upgrade hint
- File lock (`portalocker`) retained as defense-in-depth alongside daemon-mediated writes

**Affects:** C02 (daemon design), C03 (spec infra writes), C05 (CLI rewrite), C06 (TUI reactivity), C07 (event bus subscribers), C09 (quality — daemon-mode tests).

### V2 — Three-tier specs: Phase + Iter + Wave

**Decision.** Each scope level carries its own typed spec with own schema, validator, mockup requirement, audit check:

- **PhaseSpec** — phase charter: outcome statement, KPIs, success/failure modes, dependencies on prior phases, EU envelope, ship criteria
- **IterSpec** — iter intent: sub-goal within phase, ordering rationale, wave grouping rationale, audit cadence
- **WaveSpec** — wave deliverable: verdict citations, file scopes, behaviors, failure modes, tests, mockup (UI scopes only)

**Authoring cost mitigation.** Spec scaffolding CLI generates ~80% of each spec from prior context:

- `eawf phase spec init <phase-id>` — pulls phase title + iters + waves from `state.json`, seeds outcome from `roadmap propose` input
- `eawf iter spec init <iter-id>` — inherits phase context, lists waves under iter, requests sub-goal text
- `eawf wave spec init <wave-id>` — inherits iter context, requests verdict citations + mockup if UI scope

**Storage paths.**
- `.ea/specs/<phase>/spec.md` — PhaseSpec
- `.ea/specs/<phase>/<iter>/spec.md` — IterSpec
- `.ea/specs/<phase>/<iter>/<wave>.md` — WaveSpec

**Affects:** C03 (spec schemas), C04 (workflow skills — `/roadmap propose` emits PhaseSpec; `/prep` emits IterSpec scaffold; `/flow` claim emits WaveSpec scaffold), C05 (CLI verbs).

### V3 — Composable profile bundle with declared precedence

**Decision.** Project carries `profiles: [research, engineering, reverse-engineering, spike, ...]` ordered list. Each profile declares `conflicts_with: [...]` and `overrides: [...]`. Loader fails fast if conflict undeclared. Project carries explicit `profile_priority: [a, b, c]` for tie-breaks. Effective ruleset = union of profile contributions, conflict-resolved by precedence.

**Profile contributions per profile:**

- Default skill set (which `/skills` are enabled)
- Default hooks (pre-commit, prepare-commit-msg, commit-msg)
- Default templates (research brief, ADR, hypothesis, audit kind)
- Default validation rules (which strict checks apply)
- Default config layer values (defaults that the project can override)

**Profile bundle examples:**

- `[research]` — academic-style spike + hypothesis-driven; light shipping gates
- `[engineering]` — feature-PR-driven; full lint/test/coverage gate
- `[research, engineering]` — research substrate + ship-ready gate (most common; Eawf itself uses this)
- `[reverse-engineering, research]` — symbol-naming + hypothesis-driven decompilation; specialized templates
- `[spike]` — short-lived; minimal gate; promote-on-graduation flow

**Affects:** C08 (config + profile composition), C04 (skill loader reads profile bundle), C10 (docs/templates per profile), C03 (spec validators conditional on profile).

### V5 — Runtime fallback: reactive switchover on error

**Decision.** Daemon uses **reactive auto-switch** on primary-runtime failure (HTTP 429 / 5xx / timeout / API-error). No active health-probe. On error, daemon flips the affected wave to the next runtime in the configured preference ladder and re-issues the dispatch envelope against that runtime with the idempotency key preserved.

**Rationale.**

- Reactive matches existing failure semantics — daemon already sees the non-zero exit / error envelope from `claude -p` and equivalents.
- Skips probe cost (every minute × every runtime). Probes age fast and miss the runtime calls that actually matter to a wave's progress.
- Reuses the same 429 vendor-pause logic from `2026-05-15-long-term-roadmap-synthesis.md:132,221` (auto-pause + banner overlay) — extends it from "halt" to "switch then halt-on-no-backup".

**Configurable surfaces.**

- `<local-path>`: `runtime.preference: [claude, codex, opencode]` — ordered ladder; first entry = primary
- Per-scope override: `.ea/config.yaml runtime.preference: [...]`; per-wave override at `state.waves[*].runtime_preference: [...]`
- Switch-on-error policy: `runtime.fallback.on_errors: [429, 5xx, timeout]` (default); operator may narrow
- Notification path: TUI banner + `runtime_switched` event on `event.jsonl` + OS notification (deferred to v0.5 telemetry surface)

**Hard non-negotiables.**

- Switchover never silently rewrites `Wave.runtime`; daemon emits a `runtime_switched` event with `from`, `to`, `cause` fields so audit replay shows the trace
- If every runtime in the preference ladder fails, daemon halts the wave with `BLOCKED` status and emits an operator-notify event — never picks an undeclared runtime
- Switchover is per-wave; other waves continue on primary unless they also fail
- Operator-manual override: `eawf wave switch <wave-id> --to <runtime>` forces a switch independent of error state

**Affects:** C02 (daemon error-handling + retry/redispatch path), C07 (agent-dispatch runtime-pick logic; per-runtime adapter must surface error-class consistently), C08 (config fields `runtime.preference` + `runtime.fallback.*`), C09 (event kind catalog + audit replay).

### V6 — Cross-platform daemon: per-OS native service + on-demand spawn

**Decision.** Daemon bootstraps natively on each supported OS using each platform's idiomatic service-registration surface, layered on top of the on-demand spawn from V1:

- **Linux**: `systemd --user` unit at `<local-path>`. Auto-start via `systemctl --user enable eawfd`.
- **macOS**: `launchd` LaunchAgent plist at `<local-path>`. Auto-load via `launchctl load`.
- **Windows**: per-user Windows Service via `pywin32` (`win32serviceutil`) or NSSM wrapper. Auto-start on logon.

Auto-start on login is **opt-in** via `eawf daemon enable` (writes the service file + registers it). On-demand spawn from V1 remains the default — even with auto-start off, daemon spawns on first CLI mutation and idles down after the configured timeout.

**Rationale.**

- Native UX per OS — no surprise non-idiomatic service file.
- Docker container path considered (operator explicitly raised); rejected — a ~5K-LOC validator + JSON-RPC inside a container is overkill, breaks file-IO assumptions on bind-mounted state, and adds an image-rebuild step on every release.
- WSL-only-on-Windows rejected — leaves Windows-native users unsupported.

**Cost accepted.**

- Three service-file authoring paths + three install/uninstall paths. Each ~80-150 LOC.
- `pywin32` dependency on Windows (heavy but standard) OR NSSM bundled in installer (smaller dep, separate binary). Pick deferred to C02.
- Portalocker behaviour verified per OS in CI matrix: POSIX `fcntl` on Linux/macOS; `LockFileEx` on Windows. The Windows file-ID portability concern raised in `2026-05-15-state-history-cache-design.md:277` is addressed by deriving cache keys from `sha256(repo-path + relative-path)` rather than OS file IDs.

**Hard non-negotiables.**

- Daemon never requires the auto-start service file to function — on-demand spawn covers all paths
- Service-file install/uninstall is reversible; `eawf daemon disable` removes the file cleanly
- One service file per user (no system-wide multi-user daemon in v0.3 → v0.5; V1 already locks single-user)
- CI tests the on-demand spawn path on all three OSes; service-registration path tested manually pre-release

**Affects:** C02 (daemon bootstrap + spawn + service-registration verbs `eawf daemon enable|disable|status`), C05 (`eawf daemon` CLI verb surface), C09 (per-OS CI matrix; portalocker behaviour tests), C10 (release packaging includes service-file templates).

### V7 — Telemetry: vendor agent-lens schema, rebuild inside eawf

**Decision.** Telemetry lives inside eawf, not as a separate sidecar. **Audit the private `agent-lens` repo** at `https://github.com/Elementarno9/agent-lens`, extract its data model + visualization patterns + storage choices, then implement the equivalent under `src/eawf/telemetry/` backed by a user-scope store at `<local-path>`. After parity, agent-lens is deprecated; eawf is the single tool.

**Storage.** User-scope DuckDB (preferred; OLAP-shaped workload — window functions + rolling aggregates) or SQLite (fallback if DuckDB dep cost too high) at `<local-path>`, fed by:

- Per-repo `event.jsonl` projections (`incident`, `audit_*`, `agent_end`, `wave_close`, `runtime_switched` events)
- Per-runtime session logs (`<local-path>`, Codex equivalent under `<local-path>`, OpenCode equivalent) parsed into typed rows
- Per-dispatch envelope metadata (tokens, cache hits, EU, runtime, elapsed)

**Metrics catalog (initial — refined when agent-lens audit lands).**

- Tokens burnt per session / wave / phase, split into input / output / cache-create / cache-read
- Session execution efficiency: EU delivered / EU planned; cache-hit ratio; turn count vs goal complexity
- Errors + cause classification: incident-cause taxonomy (specced in C09 from the existing `Incident` model)
- Statistics over time: rolling 7d / 30d / 90d burn rate; p50 / p99 latencies; switchover frequency
- Per-runtime breakdown: CC vs Codex vs OpenCode token costs + outcomes
- Cache-control health: `cache_creation_input_tokens` vs `cache_read_input_tokens` ratio — mis-layer alarm per `2026-05-15-long-term-features-deep.md:599`

**Surfaces.**

- CLI: `eawf metrics show [--scope user|repo|phase] [--window 7d]`, `eawf metrics export --format prom|json|csv`
- TUI: `/metrics` overlay rendering dashboard tiles per `2026-05-16-p20-tui-design-direction.md:541`
- Optional Prometheus textfile-collector output for power-user dashboards

**Rationale.**

- Single tool — operator never learns or installs two CLIs.
- Vendor-then-rebuild preserves agent-lens design wins without coupling eawf to agent-lens's dep / shape choices.
- User-scope DB (not per-repo) supports cross-repo aggregates natively — weekly burn rate across all projects in one query.
- DuckDB chosen over SQLite for the OLAP shape; falls back to SQLite if DuckDB adds too much install weight.

**Hard non-negotiables.**

- Telemetry opt-in by default — `telemetry.enabled: false` until operator sets it
- No data leaves the machine without explicit `telemetry.export.endpoint` config (no implicit phone-home)
- Per-repo `event.jsonl` remains canonical; user-scope DB is a projection, rebuildable from a full `event.jsonl` sweep
- Schema versioned; loader fails fast on unknown `schema_version`
- agent-lens schema citations recorded explicitly in C09 brief Provenance for attribution

**Affects:** C07 (event-bus emit points; per-dispatch envelope metadata fields), C08 (config fields `telemetry.*`), C09 (telemetry subsystem spec + agent-lens audit + DB schema + visualization surface), C10 (CLI verb `eawf metrics`, opt-in onboarding flow).

### V8 — Agent dispatch: hybrid session reuse

**Decision.** Dispatch policy is **hybrid**:

- **Fresh process** per **new wave** dispatch — clean context, full KV-cache hit on the stable prefix, deterministic token cost.
- **Reuse session** (`claude --continue <session-id>` / Codex `--resume` / OpenCode equivalent) on **retry / edit / follow-up against the same wave** — preserves turn history, avoids re-explaining state.

Daemon tracks the session handle per `(wave_id, attempt_id)` and routes retry envelopes back to the existing session.

**Rationale.**

- New wave = new task; fresh context is correct and cheaper (full prefix cache hit).
- Retry = same task with corrections; session reuse preserves what the agent already knew.
- Avoids context-window blowout — retry/edit additions are small relative to a full new-wave re-spawn.
- KV-cache strategy from `2026-05-15-long-term-features-deep.md:42,201-249,605,613` and bio-memory consolidation from `2026-05-15-long-term-features-deep.md:125-157` both remain valid — fresh dispatch carries the consolidated memory + cached prefix.

**Per-runtime session-handle paths.**

- Claude Code: `<local-path>` (existing path; mentioned in `2026-05-15-long-term-roadmap-synthesis.md:121`)
- Codex CLI: `<local-path>` (verify in C07)
- OpenCode: vendor-specific (verify in C07)
- Daemon persists `state.waves[wave_id].sessions: { attempt_id: { runtime, session_id, started_at, ended_at } }` so audit replay can reconstruct dispatch history

**Operator override.** Skill manifest declares `dispatch.session_policy: fresh | continue | hybrid`; default `hybrid`. Skills that know better override — e.g., `/audit` always wants `fresh`; `/coauthor` always wants `continue`.

**Cache-control interplay.**

- Fresh dispatch: stable prefix (AGENTS.md + state digest) carries `cache_control: 5m`; full hit-or-write path applies per `2026-05-15-long-term-features-deep.md:580`.
- Continue dispatch: session has its own internal cache; eawf does not re-issue cache markers — runtime SDK handles continuation cache automatically.

**SDK tradeoff (preview; full matrix in C07).**

- `claude-code` CLI subprocess: current default; supports `--continue <id>`; rich session-file layout
- `claude-agent-sdk` Python: rejected for Pro/Max subscribers per `2026-05-15-long-term-roadmap-synthesis.md:21,102` (BYOK-only); programmatic session control nicer if BYOK constraint relaxes
- Codex CLI subprocess: matches CC pattern; session-resume verified in P15
- OpenCode CLI subprocess: verified in P15+
- Final pick: **subprocess CLI per runtime as primary path**; SDK adoption deferred unless BYOK constraint relaxes

**Hard non-negotiables.**

- Session handles tracked in `state.waves[*].sessions` (daemon-written; audit-replayable)
- Switching runtime mid-wave under V5 fallback starts a fresh session on the new runtime — session handles are runtime-specific, never portable
- `--continue` failures (session expired, file deleted) fall back to fresh dispatch with explicit `Wave.dispatch_history` annotation
- Skill manifest `dispatch.session_policy` is profile-gated per V3: research-profile skills may default `continue`; engineering-profile skills may default `fresh`

**Affects:** C02 (daemon session-handle tracking; per-(wave, attempt) routing), C04 (skill manifest `dispatch.*` fields), C07 (agent-dispatch session-reuse implementation; per-runtime adapter session-handle surface; full SDK tradeoff matrix), C08 (per-profile session-policy defaults), C09 (session-reuse metrics; context-window pressure tracking).

### V9 — Native per-runtime plugins remain first-class distribution channel

**Decision.** eawf continues shipping per-runtime native plugins as the primary skill / hook / command / agent / statusline distribution channel. Each supported runtime carries its own plugin tree under `build/<runtime>-plugin/` matching that runtime's native plugin shape:

- **Claude Code**: `build/eawf-plugin/{skills,hooks,statusline,commands,agents}/...` (current canonical layout established by P04; installed locally under `<local-path>` and `.claude/`)
- **Codex CLI**: `build/codex-plugin/...` matching Codex plugin discipline (per P15 adapter)
- **OpenCode**: `build/opencode-plugin/...` matching OpenCode plugin discipline
- Future runtimes (Aider / Cursor / Cline per G4 goal set): each gets its own plugin tree at adoption time

**Rationale.**

- Native plugin format gives the operator each runtime's native UX — slash commands surface natively; hooks fire on the runtime's events; statusline integrates per runtime.
- Subprocess-CLI dispatch (V8) is for **calling** runtimes; native plugins are for **decorating** them with eawf's skill / hook surface. Orthogonal concerns — both must coexist.
- AGENTS.md is the single source of truth; per-runtime plugins are sync'd projections (P04 already follows this).
- Avoids the "one giant cross-runtime wrapper" anti-pattern that fights every runtime's plugin conventions.

**Plugin sync.**

- `eawf plugin sync [--runtime <name>]` re-generates per-runtime plugin contents from AGENTS.md + the shared skill registry (C04) + per-runtime adapter rules (C07).
- Sync triggers: AGENTS.md edit, skill registry update, runtime adapter capability change. Pre-commit hook covers AGENTS.md drift; post-`/research --final` or post-`/design` hooks regen affected plugin bundles.
- Verification: `eawf plugin doctor` walks each runtime's plugin tree and flags drift vs canonical source (file count, file hash, registered skill list, hook count).

**Profile contribution (V3 interplay).**

- Profiles declare skill / hook / template / statusline contributions; plugin sync writes the profile-resolved bundle into each runtime's plugin tree.
- Disabling a skill in `.ea/config.yaml profiles:` → next sync removes it from each runtime's plugin tree.
- Conflict-resolution + override semantics from V3 apply at the contribution layer, not at the plugin layer.

**Source-vs-install distinction.**

- **Canonical sources** live under `build/<runtime>-plugin/` — committed to the repo so contributors edit the source of truth.
- **Per-machine install paths** are local-only — `.claude/`, `<local-path>`, OpenCode-equivalent — generated by sync; gitignored per `feedback_claude_local_only.md`. CI tests the sync output against fixtures; never reads the install path directly.

**Hard non-negotiables.**

- Native plugin distribution is NOT optional — every supported runtime ships with one.
- Plugin source under `build/<runtime>-plugin/` is the canonical, committed form. Install paths are gitignored renders.
- `eawf plugin doctor` MUST flag drift; never auto-fix without operator confirm (drift may be operator-edited install, lose-the-edit risk).
- New runtime adoption gates on (a) native plugin shape understood, (b) capability matrix filled in C07, (c) `build/<new-runtime>-plugin/` scaffolded, (d) sync verb supports it.
- Subprocess-CLI dispatch (V8) and native plugin distribution (V9) are independent — disabling either keeps the other operational.

**Affects:** C04 (skill registry contributes to plugin sync output), C07 (plugin/runtime arch B5 + manifest schema + sync verb + doctor verb; per-runtime native plugin shape catalog), C08 (profile-contribution-to-plugin pipeline), C10 (release packaging ships canonical plugin trees per runtime; install/upgrade docs cover sync invocation).

### C02 — Daemon + Topology + Security spine

**Scope statement.** Locks the daemon architecture: IPC protocol, lease/lock model, supervisor + spawn semantics, event bus, subscription model, resource limits, security boundary. This cluster makes V1 implementable.

**Goals.**
- IPC protocol pick: Unix domain socket + JSON-RPC 2.0 (default) vs gRPC vs msgpack-RPC vs Cap'n Proto
- Lease/lock semantics: how daemon arbitrates writes; what happens on daemon crash mid-write
- Spawn model: auto-spawn from CLI on first mutation; PID file at `<local-path>`; socket at `<local-path>` (or `$XDG_RUNTIME_DIR/eawfd.sock`)
- Idle-timeout shutdown (default 300 s configurable)
- Subscription bus: TUI subscribes to event stream; daemon pushes envelope on mutation
- Job queue: how `/flow` parallel dispatch enqueues work; how scheduler honors wave DAG + EU budget + concurrency cap
- Supervisor: how the daemon restarts crashed subprocesses (agent runtimes, audit-DSL workers)
- Resource limits: max parallel agents, EU budget per session, time budget per wave, OOM kill thresholds
- Version skew handling: CLI v0.4 against daemon v0.3 → fail with upgrade hint
- Security boundary: socket file permissions (0600), auth token model (per-user only for v0.3 → v0.5; multi-user deferred to v0.6+), prompt-injection defense at IPC boundary
- Recovery: PID stale detection, lock-file cleanup on startup, audit-log replay for in-flight transactions
- Process topology diagram: CLI / TUI / web / eawfd / agent runtimes

**Non-goals.**
- Multi-user / multi-tenant daemon (deferred to v0.6+; lock single-user invariant here)
- Network daemon (Unix socket only for v0.3 → v0.5)
- Hot-reload of daemon code (always full restart)

**Prior verdicts cited.** V1 (daemon Day-1 + smart spawn), V5 (reactive runtime fallback), V6 (per-OS native service + on-demand spawn), V8 (session-handle tracking).

**Additional goals (from V5, V6, V8).**

- **Per-OS service-registration spec** (V6): `<local-path>` template (Linux), `<local-path>` template (macOS), Windows Service via `pywin32`-`win32serviceutil` OR NSSM wrapper (decide in C02 brief). `eawf daemon enable|disable` writes/removes the service file. On-demand spawn (V1) remains default; service-registration is opt-in.
- **Portalocker per-OS verification matrix** (V6): POSIX `fcntl` on Linux/macOS; `LockFileEx` on Windows. CI matrix exercises both code paths on the on-demand-spawn surface.
- **Runtime fallback handler** (V5): error-class detection (HTTP 429 / 5xx / timeout / API-error from runtime subprocess output), runtime-ladder traversal per `runtime.preference`, `runtime_switched` event emit with `from`, `to`, `cause` fields. Operator-manual override `eawf wave switch <wave-id> --to <runtime>` bypasses error-state requirement.
- **Session-handle tracking** (V8): daemon persists `state.waves[wave_id].sessions: { attempt_id: { runtime, session_id, started_at, ended_at } }`. Retry/edit dispatch envelopes route to the existing session via the persisted handle; new-wave dispatch always opens a fresh subprocess.
- **Idempotency keys** (V5): dispatch envelopes carry an idempotency key so cross-runtime re-issue after fallback does not double-execute side effects.

**Key axes to lock.**
- IPC pick: JSON-RPC over Unix socket is simplest (stdlib-friendly); msgpack faster but Python tooling weaker; gRPC heavy for local IPC. Recommend JSON-RPC.
- Auth model: socket file permissions vs token vs Unix peer credentials (SO_PEERCRED on Linux, LOCAL_PEERCRED on BSD/macOS). Windows: named-pipe ACL — confirm against pywin32 surface.
- Process pool design: daemon spawns short-lived workers per agent invocation vs maintains warm pool
- Backpressure: how the bus handles slow subscribers
- Migration plan from current state-CLI-as-writer: phased — daemon ships, CLI proxies to daemon if present + retains direct file IO if absent, then later versions remove direct file IO from CLI writers
- Crash safety: daemon must write WAL before applying transaction so replay is possible
- Windows daemon transport (V6): Unix-socket-only is the v0.3 → v0.5 invariant; on Windows, use named pipes (`\\.\pipe\eawfd-<user>`) with equivalent semantics. Confirm pywin32 or stdlib `asyncio.start_unix_server` Windows-equivalent.
- pywin32 vs NSSM on Windows (V6): pywin32 is a heavy dep with proper Service hooks; NSSM is a small bundled binary wrapper. Tradeoff decided in C02 brief — installer complexity vs dep weight.
- Service-file uninstall safety (V6): `eawf daemon disable` MUST be idempotent and never leave dangling launchd / systemd / svc entries
- Runtime-fallback retry semantics (V5): exponential backoff per-runtime before falling through to next runtime in ladder? Or fall through immediately? Pick affects 429-burst behaviour
- Session-handle expiry (V8): how long does daemon keep a session handle live after wave close? Drop on wave-close vs N-day TTL for re-open?

## Cross-cluster invariants

Constraints every cluster brief MUST honor (lifted from AGENTS.md non-negotiable rules):

1. **CLI is dispatch; library implements** — every cluster's CLI verb sketch keeps the body in the library
2. **Strict config validation** — every YAML/JSON ingestion path uses Pydantic v2 `BaseModel` with `ConfigDict(extra="forbid")`
3. **`.ea/` is committed** (with `.ea/locks/` and `.ea/local/` gitignored) — including new `.ea/specs/`
4. **State CLI (or future daemon) is the only mutator** — no direct file writes from skills, agents, or ad-hoc scripts
5. **Symbol conventions** — `^[A-Z][A-Z0-9_-]{1,15}$` for project/phase IDs; `H<NN>-<NN>` for hypotheses; `P<NN>` for phases; `W<NN>` for waves
6. **Deletion rule** — three preconditions (committed, motivated, enumerated); never delete schemas, fixtures, license, changelog, uncommitted
7. **State vs specs** — specs describe intent; state reflects reality
8. **Verify before claiming** — every behavioral claim cites source file
9. **f-strings only**, full type hints, `from __future__ import annotations`, `logger = logging.getLogger(__name__)`
10. **`uv run` for all Python invocations**
11. **Worktree discipline** — branch from feature HEAD, cherry-pick (never merge), claim-order enforced
12. **Branch currency** — fetch + rebase before opening phase/iter/wave
13. **Pre-commit before commit** — hooks root-caused, never `--no-verify`'d
14. **Commit prefix** — `[P<NN>(-W<NN>|-CORE)] <type>: <summary>`; types include `state` for `[P<NN>-CORE] state: ...`
15. **Branch naming** — `feature/<symbol>-v<X.Y>` long-running, `feature/<symbol>-v<X.Y>-pNN-wMM` per-wave
16. **Secrets and PII hygiene** — never commit local paths, hostnames, emails (other than canonical author block), credentials, tokens
17. **Naming conventions** — `scope_id` (never `scope`), `output_dir` (never `out_dir`), `wave=` (never `wave_id=`) in logs; mutator-path precision in success criteria
18. **Artifact chassis and citations** — Summary / References / Provenance / Scrub; dense `[N]` citations
19. **Typed agent reports** — `AgentReportBody` + `AgentReportVerdict` exact enum
20. **Planned-scope revisability** — status-tiered mutability (PLANNED freely mutable; ACTIVE append-only; CLOSED immutable except reopen)
21. **Roadmap procedure** — research → propose → revise → apply → prep (no shortcuts)
22. **Spike workflow** — `/research` brief under `.ea/local/<YYYY-MM-DD>-<slug>.md`

Each cluster brief is consumed by a separate fresh CC session. To unblock a future session, the operator provides:

1. This index brief path (`.ea/local/research/long-term/2026-05-16-c00-spec-index.md`)
2. The target cluster ID (`C0N`)
3. Any cluster briefs in `depends_on` that are now `accepted`

The session opens by reading this index for verdicts + scope, reads all `depends_on` briefs for cited decisions, then writes the cluster brief following the contract above.
