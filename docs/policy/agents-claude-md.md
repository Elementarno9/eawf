# AGENTS.md and CLAUDE.md policy

*Hard rule: CLAUDE.md is a shim; AGENTS.md is the canonical agent contract.*

## Hard rule

```text
CLAUDE.md must always contain only a link / include / shim to AGENTS.md.
```

Examples:

```markdown
@AGENTS.md
```

or, if a runtime needs prose:

```markdown
See AGENTS.md. This file is intentionally only a compatibility shim generated by Eä.
```

## AGENTS.md generation

`AGENTS.md` is generated by `eawf` from:

- `.ea/config.yaml`
- selected and composed profiles
- the selected generation's current summary
- project-specific rules gathered during install
- managed template version

AGENTS.md may contain user-maintained custom regions, but Eä owns the canonical generated contract.

## Render-layer note

Profile composition MUST complete before AGENTS.md is rendered. Rendering from the raw selected profile list (instead of the merged result) skips conflict resolution, severity escalation, and removed-rule enforcement, producing AGENTS.md content that contradicts the composed config. The installer and `eawf sync` both enforce this order; a render pass that finds `composition` absent or stale aborts with `state.health: needs_setup`.

## Strong generated language

Eä always renders the following authority block into AGENTS.md (exact phrasing may evolve, but the rules stay):

```text
State is authoritative. The selected generation document records the
status of every Track, Milestone, Batch, Task and Run, with the
evidence, decisions, hypotheses, audits and artifacts behind them.

Only the eawf daemon may write the generation document, its ledgers
and the stores. Change them through the eawf entity verbs; a direct
write is refused.

Use Eä terms exactly as defined. Do not redefine Project, Track,
Milestone, Batch, Task, Run, PlanRevision, Hypothesis, Audit,
Decision or Artifact in project docs.

Do not claim completion without fresh evidence. Agent summaries are not
evidence. Commands, metrics, tests, audits, artifacts, commits, and
review findings are evidence.

Do not silently deviate from an approved PlanRevision or Task. If
discoveries invalidate scope, record the scope delta and change the
plan through eawf.
```

## AGENTS.md generated rule modules

Eä generates AGENTS.md from modular rule blocks. Profiles enable / disable blocks; user decisions persist in `.ea/config.yaml`.

### Rule schema

Each rule entry under `rules.add` accepts:

```yaml
rules:
  add:
    - id: verify-before-claiming      # required, stable, kebab-case
      severity: required              # required | recommended | optional
      summary: "Verify quantitative claims against actual code path before assertion."
      body: |
        Verification ladder, in order:
        1. Read source file
        2. grep for actual call sites in active branch
        3. Inspect run artifacts if claim is about a measured run
        4. Quote the number only after the above
      cite: docs/specs/verify-before-claiming.md   # optional, link to deeper spec
```

Render rules:

- `summary` is the canonical one-line bullet rendered into the rule module's bullet list.
- `body` is optional markdown rendered as a nested subsection under the bullet. Bullet lists, code fences, tables, and inline links are preserved verbatim.
- `cite` renders as an inline `→ <path>` link after the summary.
- Rules without `body` render as plain bullets.
- `severity: required` rules are always rendered; `recommended` and `optional` may be hidden by config filters.

### Composition

When two profiles `add` rules sharing the same `id`, the strictest `severity` wins; `body` from the higher-priority profile replaces, never concatenates (use `extends` for additive composition).

### Core rule modules

Generated AGENTS.md typically renders the following rule blocks (profile-gated):

#### Core authority

- `AGENTS.md` is canonical; runtime-specific files (`CLAUDE.md`, OpenCode config notes) are shims or generated adapters.
- State is authoritative for lifecycle. Docs explain; state decides current status.
- Only the daemon writes state and stores, reached through the `eawf` entity verbs.
- Generated regions are not hand-edited; use `eawf sync`.

#### Think twice before solution

- Before proposing the final solution, perform a second-pass review: assumptions, failure modes, simpler alternatives, long-term maintenance, evidence quality.
- For non-trivial work, use `/research`, `/spike` or parallel read-only agents before `/plan`.
- For significant code changes, run a fresh-context `/verify` before integrating.
- Do not trust subagent conclusions blindly; reconcile contradictions.

#### Prefer durable solutions

- Prefer steady, stable, long-term fixes over hardcoded hotfixes.
- Root-cause before patch. If quick mitigation is needed, record it as temporary with a draft Task and removal condition.
- Avoid scope creep, but do not choose brittle shortcuts that increase future risk.
- Keep behavior-defining config in committed config files, not hidden local edits.

#### Evidence before completion

- Do not claim done without fresh evidence: command outputs, audits, metrics, tests, review findings, artifacts, commits, or PR checks.
- Agent summaries are not evidence.
- If a configured check cannot run, record why and mark evidence incomplete.

#### AskUserQuestion policy

- Prefer structured `AskUserQuestion` with options, not free-form waiting.
- Ask when: destructive / shared action, missing secret / auth, ambiguous product decision, external resource required, or same sub-goal failed 3 times.
- Include: blocked condition, tried attempts, 2–4 options, recommended option.
- Background subagents must route blockers to controller; controller asks user.
- Do not ask for reversible low-stakes choices; choose safe default and record it.

#### Parallel agents

- For complex read / research / review tasks, prefer parallel subagents.
- Default max subagents per session: configurable, recommended 10; hard ceiling configurable 20.
- Parallel write agents require disjoint write claims or explicit merge owner and usually worktrees.
- Controller must synthesize and verify subagent findings.

#### Planning and Task discipline

- Use `/research → /plan → /dispatch → /verify → /integrate → /accept` for non-trivial work.
- Do not silently deviate from an approved PlanRevision or Task.
- If discovery invalidates the plan, stop and re-plan through a new PlanRevision.
- Completed Milestones, Batches and Tasks are immutable; rework appends a new Batch or Task.

#### Worktrees and VCS safety

- Use worktrees for parallel writers, risky edits, dirty-root interruptions, and PR merge-ref testing.
- Never force-push protected branches.
- Never skip hooks / checks unless policy and user approval allow it.
- Never commit secrets; run secret scan before every commit when configured.

#### Memory hygiene

- Promote durable lessons through `/memory`; do not dump raw chat history into memory.
- Mark stale / superseded memories instead of deleting unless the deletion policy passes.
- Keep injected memory compact and scoped.

#### Deletion safety

- Delete only if recoverable from git, justified by explicit decision / audit / verdict, and listed in the commit / PR body.
- Never delete data, run artifacts, reports, or uncommitted user files without explicit approval.

#### Response style

- Be concise and direct.
- Preserve paths, commands, errors, evidence, decisions.
- Avoid long summaries unless asked.
