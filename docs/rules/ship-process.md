# `ship-process`

Ship a Milestone through one PR: squash to one commit per Batch before review, fix review findings by appending Batches, accept last, then fast-forward main to the reviewed commit.

### Ship process

Ship is the Milestone's terminal pass, under decision D88, proposed to supersede D87 and pending operator ratification. The ordered steps from landed Batches to a merged, tagged Milestone:

1. **Squash before review.** Before review opens, ``eawf batch squash`` writes the long-running feature branch again as one commit per Batch (a few for a large Batch), each carrying its ``Batch:`` and ``Task:`` trailers, plus one trailing ``state:`` commit, and proves its tree equals the source tip's. Once the branch points at it, ``eawf batch rebind`` appends a superseding row for every binding that named a source commit. Each Batch already closed when it landed: the daemon bound the Milestone branch head and walked the Batch and its Tasks to COMPLETED. A pushed branch is rewritten only before review opens, only with ``--force-with-lease``, and only after writing an archive ref of the old head.
2. **Open the Milestone PR.** One PR per Milestone, body per the ``pr-template``. From this point the commits on the branch are fixed: every commit a reviewer reads is the commit that merges.
3. **Pass CI gates.** Beyond the per-commit lint + test gauntlet, two gates fire only on the Milestone PR and so are easy to miss locally: the per-package **coverage gate** (CI parses ``coverage.xml`` against the ``[tool.eawf.coverage]`` thresholds) and the **snapshot-pairing gate** (``tools/snapshot_pairing_gate.py`` over the PR base..head range, which rejects a managed golden-surface mutation whose commit names no Batch or Task of the generation). Run both locally before pushing the PR so they do not surface late.
4. **Append after review.** ``/verify --mode review`` runs the review pass over each Batch. Fix each finding by appending a new Batch to the Milestone, with its own commit and one trailing ``state:`` commit per push. After review opens, do not squash, amend, rebase or force-push the branch, and do not open a second PR. Ledgers stay append-only: a correction is an appended superseding row.
5. **Accept last.** Accept the Milestone only when CI is green on the pushed head and the review has no open findings. The acceptance and its version bump ride the last ``state:`` commit on the branch; no commit lands on the branch after it.
6. **Merge by fast-forward only.** Fast-forward ``main`` to the reviewed, accepted head, so each Batch commit lands on ``main`` with its reviewed SHA and every binding stays valid. Do not make a merge commit, a squash merge or a rebase merge. When ``main`` has moved past the branch base, the fast-forward fails: stop and ask the operator. main and tags are never rewritten.
7. **Release at merge.** The Milestone is release-ready at merge: the release verbs check it before anything is tagged (see ``release-process``), and nothing after the merge is Milestone work. A repo that releases through an eawf release train then runs ``eawf release pipeline <version> --milestone <MLS-NNNN> --publish`` from a clean checkout of the merge commit: one journaled, resumable walk that tags and pushes only with ``--publish``, waits for the publish runs, pins, proves, approves and observes the checkpoint to BAKED, advances the train, checks each completed Batch's commits on ``main`` by their ``Task:`` and ``Batch:`` trailers, and stages the evidence for one ``state:`` commit. A refused step names its reason and a rerun resumes there, so the next Milestone carries no release Tasks; every other repo keeps its own tag flow. Nothing publishes until the tag is pushed.
