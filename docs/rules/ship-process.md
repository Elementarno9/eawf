# `ship-process`

Ship rides the phase-co-closing iter: open the one phase PR, pass CI, address review by appending waves to that same iter, then close and fast-forward main.

### Ship process

Ship is the phase's terminal pass, and it rides the phase-co-closing iter (the final iter of the phase) rather than a fresh iter. The ordered steps from green waves to a merged, tagged phase:

1. **Open the phase PR.** One PR per phase, body per the ``pr-template`` (``## Summary`` + ``## Test plan`` + ``## Phase deliverables``). The PR head is the long-running ``feature/<symbol>-v<X.Y>`` branch with every worktree wave already cherry-picked in.
2. **Pass CI gates.** Beyond the per-commit lint + test gauntlet, two gates fire only on the phase PR and so are easy to miss locally: the per-package **coverage gate** (CI parses ``coverage.xml`` against the ``[tool.eawf.coverage]`` thresholds) and the **snapshot-pairing gate** (``tools/snapshot_pairing_gate.py`` over the PR base..head range, which rejects a managed golden-surface mutation that lacks a wave-form ``test:`` subject). Run both locally before pushing the PR so they do not surface late.
3. **Pass the review.** ``/ship`` runs the PR review pass. Address feedback by **appending waves to the same co-closing iter** via ``eawf roadmap revise --add-wave`` (ACTIVE-phase ``add_wave_plan`` keeps the iter ACTIVE and lands the new waves PENDING). Do NOT open a second iter for routine review follow-ups -- see ``iter-phase-close-timing``.
4. **Close + land.** Once CI is green AND the review-passed branch is on the remote, the phase-close mutation rides the single ``[P<NN>] state: close iter + phase (audit=<id>)`` commit that bundles iter close + phase close (see ``iter-phase-close-timing``). Land by fast-forward so every wave commit and its pin survive: rebase onto ``main`` locally, let CI pass on that exact SHA, then ``git push origin <branch>:main``; the push ends the phase. Never squash, and never use a hosted rebase merge, which re-creates every commit and stales every wave pin. If commits were rewritten anyway, repin each wave by its ``Eawf-Wave`` trailer on first-parent ``main``, breaking ties by ``git patch-id``; the ``wave-trailer-guard`` pre-push hook refuses a rewrite that drops a wave's trailer.
5. **Release at merge.** The phase exit criterion is release-ready at merge: under the ``per-phase`` cadence the phase cannot close without a passing release pre-flight (see ``release-process``), and nothing after the merge is phase work. The post-merge ``.github/workflows/phase-release.yaml`` checks the ``(release=v<X.Y.Z>)`` annotation off the phase-close commit against the package version and prints the release command; it pushes no tag. A repo that releases through an eawf release train then runs ``eawf release pipeline <version> --phase P<NN> --publish`` from a clean checkout of the merge commit: one journaled, resumable walk that tags and pushes only with ``--publish``, waits for the publish runs, pins, proves, approves and observes the checkpoint to BAKED, advances the train, checks the phase's wave pins by trailer, and stages the evidence for one ``[P<NN>] state:`` commit. A refused step names its reason and a rerun resumes there, so the next phase carries no release waves; every other repo keeps its own tag flow. Nothing publishes until the tag is pushed.
